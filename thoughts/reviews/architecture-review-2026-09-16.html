Testable only through a widget. No way to ask "what does write do with a missing field?" without picking one.

Each widget emits a small descriptor: field setters, action invokers, type name. The behaviour lives once, behind one interface — and that interface is the test surface.

Problem
buildScriptActionMethod is cc=43 — nearly triple the next worst routine in the repo — because it is a code generator emitting a whole dispatch tree. The generated behaviour is identical for all 47 widgets; only the field and action names vary.

Solution
Put the seam between invariant behaviour and per-widget data. A runtime script_bridge module in rui_core does the dispatching; the macro emits only a descriptor of names and setters.

deletion test

Complexity concentrates — the bridge earns its keep. But today it earns it 47 separate times. The complexity is accidental: it is a dispatch table written as emitted control flow.

  • ✓ cc 43 → single digits
  • ✓ Verb semantics testable directly
  • ✓ One place to fix a verb bug
  • ✓ 47 copies → 1 implementation

4. The missing seam: nothing ever clears hovered

Strong live bug
  • packages/rui/src/app.nim:391–396 the only write to `hovered` in the entire repo
  • packages/rui_core/src/types.nim:86 Widget.hovered
  • consumers: every themed widget's `render`, and basic/tooltip.nim:47

  # Update hover state: clear old, set new
  let widget = app.hitTestSystem.getWidgetAt(...)
  if widget != nil:
    if not widget.hovered:
      widget.hovered = true      # <-- set, and never unset, anywhere

A repo-wide search for writes to hovered returns exactly this one. Once a widget is hovered it stays hovered for the life of the process.

Mirrors how FocusManager already owns focus. Hover has no such owner.

Problem
There is no module owning "the pointer left this widget", so hover is a one-way latch. Buttons keep their highlight after the pointer leaves, and Tooltip, which hides itself on not widget.hovered, can never hide.

Solution
Give hover the same shape focus already has: a small module that remembers the currently hovered widget and clears the previous one on transition.

deletion test

There is nothing to delete — the module was never written. The symptom is spread across every widget's render, which is exactly what missing locality looks like.

9. Sentinel-as-absence in makeThemeProps

Speculative
  • packages/rui_drawing/src/builtin_themes.nim:14 cc=15, 14 params, 14 guards

Every parameter is non-optional and absence is inferred from a sentinel (alpha == 0, value > 0), so the body is fourteen ifs. High cc, but flat, readable, and zero coupling — and the deletion test says it concentrates complexity that would otherwise land at every call site in the builtin themes.

Listed for completeness because it is the third-highest cc in the repo. I would not touch it: switching to Option[T] params trades 14 guards here for some(…) noise at every caller. Worth an ADR to stop it resurfacing in future reviews.

Examined and left alone

  • interval_tree.nim:173 removeNode — cc=16. Essential: interval-tree deletion with rebalancing. The complexity is the algorithm.
  • widget_dsl.nim:113 buildConstructorBody — cc=9. Essential: a real AST walk over prop/state/action sections.
  • pango_text.nim — 417 lines but already a deep module: measure, cursor geometry, hit-testing and rasterisation behind a small interface, with the glyph cache as an internal seam. The one caveat is that the cache is a module-level var, so eviction cannot be tested in isolation.
  • main_loop.nim:127 renderPass — cc=10, and load-bearing for the texture model. Leave until candidate 3 settles.
  • rui_widgets — 59 files, 6,468 lines, only 5 routines over cc=5. The largest package is also the flattest; no action.
top recommendation

Start with #1 and #4 — then commit to #2

Deleting the dead text cache costs nothing and removes 428 lines plus three App procs that silently report the wrong thing. The hover latch is a live bug with a one-module fix, and it blocks the Tooltip widget from working at all. Both are an afternoon.

The scripting bridge is the real architectural win: one routine at cc=43 against a repo whose next worst is 16, emitting the same dispatch into 47 widget types, testable only by going through a widget. Moving the invariant behaviour behind one interface and emitting per-widget descriptors is the single change that buys the most locality — and it is the one that gets harder as more widgets land. Theme lookup is a close second for the same reason: 21 copies of one ladder, and a cache nothing reaches.
